# Архитектура «domio»

## Решение по бэкенду: Firebase

Принято 26.07.2026. Своего сервера не будет — используем Firebase проекта
`domio-7ad1c` (он уже заведён; конфиг — в `firebaseConfig.ts` в корне).

- **Firebase Auth** — вход клиентов и мастеров, роли, сессии.
- **Cloud Firestore** — профили, заявки, переписка. Живые подписки
  (`onSnapshot`) дают обновление статусов без опроса сервера.
- **Firebase Storage** — фотографии к заявкам вместо локальных URI с телефона.
- **Cloud Functions** — позже: подбор мастера, отправка пушей, всё, чему нельзя
  доверять клиенту.

Почему так: команда из одного разработчика, нужен realtime в чате и статусах
заявок, а бесплатного тарифа хватит на весь период проверки гипотезы. Своя
серверная часть на этой стадии — расход времени без отдачи.

Что рассматривалось и отклонено: **Supabase** (лучше для сложных отчётов и
SQL, но realtime настраивается дольше, а Firebase уже подключён), **свой
API** (полный контроль ценой недель работы на то, что здесь не нужно).

Решение обратимо: доступ к данным изолирован в контекстах вроде
`components/orders-context.tsx`, экраны про базу ничего не знают.

## Модель данных

Правила доступа в `firestore.rules` написаны ровно под эту схему — меняешь
одно, проверяй второе.

### `users/{uid}`

Профиль клиента. Читает и пишет только владелец.

```
name: string            // «Дмитрий»
email: string
addresses: string[]     // ['ул. Ленина, 24']
activeAddress: string
city: string            // «Москва» — по нему заявку находят мастера рядом
themeMode: 'light' | 'dark'
pushTokens: string[]    // экспошные токены устройств, их читает только сервер
```

### `admins/{uid}`

Список модераторов. Документ заводится **вручную в консоли Firebase** —
правила запрещают запись в эту коллекцию кому угодно, включая самих
модераторов. Иначе роль администратора выдавал бы себе любой желающий.

Прочитать можно только свой документ: приложение так узнаёт, показывать ли
раздел модерации.

### `masters/{uid}`

Анкета мастера. Наличие документа означает лишь намерение им стать; доступ к
заявкам даёт отдельный флаг `verified`, который ставит модератор. Читает
анкету любой авторизованный: клиент выбирает из предложений и должен видеть,
кто их прислал. Пишет только сам мастер — и не всё.

```
name: string
lastName: string        // фамилия; вместе с именем подписывает профиль
city: string            // пусто = видит заявки всех городов
skills: Category[]      // пусто = видит заявки всех видов
experienceYears: number | null  // стаж в годах, со слов мастера
education: string | null        // из закрытого списка components/education.ts
createdAt: timestamp

// считает сервер, правила запрещают запись этих полей кому бы то ни было
rating: number | null       // среднее по отзывам, округлённое до десятых
reviewsCount: number
completedOrders: number     // завершённые заявки, пересчёт агрегатом count()
verified: boolean           // проставит модерация, когда она появится
```

Профиль мастера клиент видит у предложения: имя с фамилией, рейтинг, стаж,
образование и число выполненных заказов. Стаж и образование — со слов мастера
и не проверяются; врать про них можно, но это видно модератору при проверке
и клиенту при встрече. А вот цифрам верить можно: `rating` нельзя было
оставить на совести владельца анкеты — мастер поставил бы себе пятёрки сам.
Поэтому его считает Cloud Function по подколлекции отзывов, а правила
сравнивают старое и новое значение и не дают их разойтись. Так же устроен
`completedOrders`: его пересчитывает сервер по завершённым заявкам, и ровно
поэтому пересчёт, а не «+1», — повторная доставка события не должна считать
один заказ дважды. С `verified` то же: единственный, кто может его изменить, —
модератор, и только этот флаг, ничего больше.

### `masters/{uid}/verification/application`

Заявка на проверку. Отдельная подколлекция, а не поля анкеты, потому что
анкету читает любой авторизованный: телефон, снимок лица и данные карты
оказались бы открыты всему приложению. Здесь их видят только сам мастер и
модератор.

```
phone: string           // 11 цифр, по нему связывается модератор
about: string           // опыт, инструмент, за что берётся
photoUrl: string | null // снимок лица в Storage

// пишет только вебхук платёжного провайдера, мастеру эти поля закрыты
cardBindingId: string | null  // токен способа оплаты, НЕ номер карты
cardLast4: string | null
cardBrand: string | null

status: 'draft' | 'pending' | 'approved' | 'rejected'
rejectionReason: string | null
appliedAt, reviewedAt, reviewedBy
```

**Как ходит статус.** `draft` заводит сам мастер; отправить в `pending` он
может только когда есть фотография — правила проверяют это, а не интерфейс.
Пока заявка `pending`, мастер её не правит: иначе можно было бы подменить
данные после того, как модератор их посмотрел. Вердикт (`approved` /
`rejected`) выносит только модератор и только с `pending`. Отклонённую заявку
мастер правит и подаёт снова.

**Почему карта не проверяется при отправке.** Сначала правила требовали её
наравне с фотографией — и заявка оказалась неотправляемой: привязать карту без
настроенного платёжного провайдера нельзя, а без карты не пускала проверка.
Тупик, в котором мастер видит «привяжите карту» и «привязка недоступна»
одновременно. Карта осталась обязательной, но решает модератор: в очереди
статус карты выведен красным, а допуск без неё требует второго касания.

Одобрение — два документа одним пакетом: `masters/{uid}.verified = true` и
`status = 'approved'`. Порознь они могли бы разъехаться, и мастер остался бы
одобренным без доступа или наоборот.

### Проверка мастера: зачем

Это единственное, что стоит между случайным человеком и списком квартир, где
сейчас никого нет. В свободной заявке лежат имя клиента, домашний адрес,
описание проблемы и фотография жилья. Пока доступ давало само наличие анкеты,
получить всё это можно было за десять секунд и без единой проверки.

Поэтому проверяются три вещи, и все три обязательны:

- **фотография лица** — снимается камерой (фронтальной) в момент заполнения,
  не выбирается из галереи. Гарантии это не даёт, но поднимает цену обмана;
  смотрит снимок живой модератор. В Storage он лежит под
  `verification/{uid}/`, куда пускают только владельца и модератора;
- **телефон** — способ связаться, если что-то не сходится;
- **привязанная карта** — банк подтверждает, что за человеком есть
  идентифицированный счёт. Заодно это будущий адрес выплат.

Чего проверка **не** делает: не сверяет лицо с документом, не проверяет
паспорт и не распознаёт ничего автоматически. Это ручная модерация, и она
ровно настолько надёжна, насколько внимателен модератор.

Юридически снимок лица — биометрические персональные данные. Для запуска в
России под него нужно отдельное согласие и своё основание обработки; это часть
работы по 152-ФЗ, которая ещё не сделана.

### Привязка карты

**Номер карты в приложение не попадает и в базе не хранится.** Мастер вводит
его на странице банка, куда его уводит `startCardBinding()`; обратно приходят
только токен способа оплаты и маска «•••• 4242». Принимать номер самим
означало бы хранить платёжные данные и подпадать под PCI-DSS — поля для
ввода карты в коде нет вообще.

Механика: функция `createCardBinding` создаёт у провайдера платёж на 1 ₽ с
сохранением способа оплаты и возвращает адрес страницы банка. После оплаты
провайдер зовёт вебхук `yookassaWebhook`, тот **перечитывает платёж у самого
провайдера** (тело уведомления не подписано, верить ему нельзя), записывает
токен и маску в заявку и возвращает рубль обратно.

**Один код на два пути.** Исход платежа приходит либо вебхуком, либо сверкой,
и оба зовут одну `settleBinding()`. Две реализации «то же самое, но для
сверки» неминуемо разошлись бы в поведении, и разошлись бы на деньгах.

**Состояние попытки** живёт в заявке: `bindingState` = `pending` → `succeeded`
| `canceled` | `failed`, рядом `bindingPaymentId`. Идентификатор платежа
обязателен — без него сверке нечего перечитывать, и недоставленный вебхук
означал бы навсегда потерянную привязку. Приложение показывает `pending` как
«проверяем оплату у банка», а не как успех: считать карту привязанной по
факту закрытия браузера нельзя, оплата могла и не пройти.

**Возврат рубля** защищён тремя рубежами: отметкой `refundedPaymentId`,
постоянным ключом идемпотентности `refund-{paymentId}` и проверкой перед
вызовом. Если возврат всё же не прошёл, ставится `refundPending`, и сверка
возвращается к нему в следующий прогон — чужие деньги единственное, что здесь
нельзя простить.

## Сверка: `reconcile`

События теряются. Вебхук может не дойти вовсе, триггер удаления — упасть на
последнем повторе. Ни то ни другое не должно требовать участия человека,
поэтому раз в 15 минут приходит `reconcile` и добирает хвосты:

| Что ищет               | Условие                                    | Что делает                                    |
| ---------------------- | ------------------------------------------ | --------------------------------------------- |
| привязки без ответа    | `bindingState == 'pending'`, старше 10 мин | `settleBinding()`; старше суток — «заброшено» |
| незавершённые возвраты | `refundPending == true`                    | повторяет возврат                             |
| застрявшие удаления    | `status == 'pending'`, старше 15 мин       | `runDeletion()`                               |
| заявки без ответа      | «Поиск мастера», 2–24 ч, нет предложений   | повторный пуш мастерам, ровно один раз        |

Своей логики у неё нет — только те же функции, что вызывают события.

**Блокировка.** Прогон берёт `system/reconcile` транзакцией: расписание может
наложиться само на себя, если предыдущий прогон затянулся, а параллельная
сверка означала бы два возврата за один платёж. Блокировка старше десяти
минут считается брошенной и перехватывается — иначе одна упавшая функция
остановила бы сверку навсегда.

Снимается блокировка в `finally`: ошибка внутри прогона не должна требовать
ручного вмешательства.

## Журнал действий

`audit/{id}` — append-only. Отвечает на два вопроса, на которые иначе ответить
нечем: кто это сделал и почему у нас такое состояние. Особенно для фоновых
операций, где никто не смотрит на экран в момент выполнения.

Три свойства делают журнал журналом:

- **писать не может никто.** Правила запрещают запись всем, включая
  модератора, — записи создаёт только Admin SDK. Править и удалять нельзя.
  Модератор здесь не исключение: он тот, чьи решения журнал и фиксирует;
- **персональных данных нет по построению.** Только идентификаторы и
  перечисления: журнал переживает удаление аккаунта, и складывать в него имя
  или адрес значило бы обойти собственное же удаление данных. Санитайзер в
  `audit.ts` вырезает то, что похоже на email и телефон, — не вместо
  дисциплины, а как последний рубеж;
- **корреляция.** `correlationId` — идентификатор события триггера или прогона
  сверки. По нему цепочка видна целиком: одно нажатие клиента, все вызванные
  им записи, все уведомления.

Записи живут 400 дней, дальше их удаляет сам Firestore по TTL-политике на
`expiresAt` (объявлена в `firestore.indexes.json`).

Читает журнал модератор.

Провайдер — ЮKassa, всё общение с ним заперто в `functions/src/payments.ts`:
переход на другого правит только этот файл. Ключи — в `functions/.env`
(см. `.env.example`); пока их нет, привязка честно отвечает «не настроено», и
заявку отправить нельзя.

### `masters/{uid}/reviews/{orderId}`

Отзыв клиента. Идентификатор — id заявки, поэтому на одну работу приходится
ровно один отзыв без всяких проверок на дубли. Оставить его может только
клиент завершённой заявки и только тому мастеру, который её делал.
Редактировать и удалять нельзя: иначе рейтинг правился бы задним числом
по договорённости.

```
orderId: string
clientId: string
clientName: string
stars: number           // 1..5, целое
text: string            // до 1000 символов, необязательный
createdAt: timestamp
```

### `orders/{orderId}`

Заявка. Клиент видит свои, мастер — взятые им и те, что ещё ищут исполнителя.
Поле `clientId` неизменяемо. Заявки не удаляются, а получают статус «Отменена».

```
clientId: string        // uid клиента, владелец заявки
clientName: string      // чтобы мастер видел, к кому едет
masterId: string | null // появляется только когда клиент выбрал исполнителя
masterName: string | null
title: string           // «Не работает розетка»
comment: string
photoUrl: string | null // ссылка на Storage либо локальный URI
address: string
city: string            // нормализованный ключ города (cityKey)
category: Category      // «электрика», выводится из объекта дома
status: 'Поиск мастера' | 'В работе'
      | 'Ждёт подтверждения' | 'Завершена' | 'Отменена'
agreedPrice: number | null  // цена выбранного предложения
agreedAt: timestamp | null
reviewed: boolean       // отзыв оставлен, второй раз не просим
createdAt: timestamp
repushedAt: timestamp   // ставит сверка: мастеров уже звали повторно; клиенту запись закрыта

// только у заявок, созданных до появления offers
price, priceStatus, priceHistory
status может быть ещё и 'Есть предложения'
```

**Жизненный цикл заявки.**

```
Поиск мастера ──(клиент выбрал предложение)──> В работе
В работе ──(мастер закончил)──> Ждёт подтверждения
Ждёт подтверждения ──(клиент подтвердил)──> Завершена
любой незакрытый статус ──(клиент)──> Отменена
```

Заявка остаётся открытой всё время, пока клиент выбирает: в этом и смысл —
предложения конкурируют. Мастер не «берёт» заявку, он присылает цену.

### `orders/{orderId}/offers/{masterId}`

Предложение мастера. Идентификатор документа равен uid мастера, и из этого
следует главное свойство схемы: **перебить чужое предложение невозможно
технически** — каждый пишет только в свой документ, а `masterId` в самой
заявке проставляет клиент, когда выбирает.

```
masterId: string        // == id документа == request.auth.uid
masterName: string
price: number           // 1..10 000 000
comment: string         // до 300 символов: когда приедет, что входит в цену
status: 'pending' | 'accepted'
orderTitle: string      // копия названия заявки, см. ниже
createdAt: timestamp
```

Видят предложение только клиент заявки и сам мастер: знать цены конкурентов
до собственного предложения незачем.

`orderTitle` — сознательная денормализация. Когда клиент выберет другого
мастера, заявка станет проигравшему недоступна, а строку в его списке надо
чем-то подписать.

**Как это заменило прежнюю схему.** До этого цена лежала в самой заявке, и
пока та числилась «в поиске», второй мастер мог переписать `masterId` и цену
поверх чужого предложения. Дыру закрывал отдельный статус «Есть предложения»,
который убирал взятую заявку из ленты, — ценой того, что заявка доставалась
успевшему первым. Подколлекция снимает и то и другое: перехват невозможен по
устройству данных, а заявка остаётся открытой для всех. Статус «Есть
предложения» остался только у заявок, созданных до этой перестройки; новые в
него не попадают.

**Что стерегут правила.** `allow update` разбит на разрешённые переходы, а
не на «кому можно писать в документ»:

- клиент меняет только `status`, `masterId`, `masterName`, `agreedPrice`,
  `agreedAt`, `reviewed` — и только теми способами, которые есть в интерфейсе
  (выбрать, подтвердить, отменить, оценить);
- при выборе `agreedPrice` сверяется с ценой в самом предложении: согласиться
  на сумму, которой мастер не называл, нельзя;
- мастер вообще не пишет ни `masterId`, ни `agreedPrice` — он может только
  отметить работу выполненной. Назначить себя невозможно;
- у заявки с уже выбранным исполнителем выбор не повторяется;
- отзыв принимается только от клиента завершённой заявки и только тому
  мастеру, который её делал.

Тесты на всё перечисленное — в `tests/firestore.rules.test.mjs`, 62 проверки.

### Как заявка находит мастера

Населённый пункт выбирается из закрытого списка (`components/cities.ts`,
около 160 пунктов по всем районам Чечни), а не вводится текстом. Свободный
ввод разводил один посёлок на несколько написаний — «Грозный», «грозный» и
«г. Грозный» были разными местами, и мастер из одного не видел заявок из
другого. Ошибка при этом тихая: заявка создаётся и просто никому не видна.
Раз обе стороны выбирают из одного списка, совпадение гарантировано.

Геокодирования по-прежнему нет: сравниваются ключи (`settlementKey` —
регистр, пробелы, «ё»), а не координаты. Радиус и карта — отдельная задача,
и до неё список закрывает ту же потребность дешевле.

**Мастер отмечает несколько пунктов** (`masters/{uid}.cities`), пустой список
означает всю республику. Лента подписывается на каждый выбранный пункт
отдельно: в Firestore допускается лишь одно «ИЛИ»-условие на запрос, а оно
уже занято специальностями. Денормализация «город+специальность» в одно поле
дала бы один запрос, но потребовала бы миграции и упёрлась бы в предел на
число значений. Общий лимит ленты делится между подписками, чтобы десять
пунктов не превратились в пятьсот заявок на телефоне.

Специальность (`Category`) выводится из объекта дома в `serviceOptions.ts`:
розетка и свет — «электрика», мойка и труба — «сантехника». Список закрытый,
потому что по свободному тексту запрос не построить.

Лента мастера: `status == 'Поиск мастера'` плюс город и `category in skills`,
сортировка по дате, `limit(50)`. Пустое поле в анкете значит «без
ограничения» — иначе мастер, не заполнивший город, не увидел бы ничего.
Составные индексы под все четыре сочетания фильтров — в
`firestore.indexes.json`; без них запрос падает.

Свои отправленные предложения мастер собирает запросом по группе коллекций
(`collectionGroup('offers')`): заявка, где он только назвал цену, ему ещё не
принадлежит, и запросом по `masterId` в самой заявке её не найти.

### `orders/{orderId}/messages/{messageId}`

Переписка клиента с выбранным мастером. Лежит внутри заявки, а не у кого-то из
собеседников: права выводятся из самой заявки, и обе стороны видят одни и те
же сообщения. Писать может только участник и только от своего имени;
отправленное не редактируется и не удаляется.

Чат открывается **после выбора мастера**. До него участник у заявки один, и
пустить туда всех откликнувшихся значило бы показать каждому переписку с
конкурентами. Поэтому всё, что мастер хочет сказать до выбора, идёт в
`comment` его предложения. Отдельный чат на каждое предложение — следующий
шаг, когда понадобится торг.

```
senderId: string        // uid отправителя, обязан совпасть с request.auth.uid
text: string            // 1..2000 символов
time: string            // «14:32» для показа
createdAt: timestamp    // для сортировки
```

Изначально переписка планировалась в поддереве пользователя, но чат по цене
принадлежит сделке, а не человеку: у мастера и клиента она должна быть общей.

### `users/{uid}/threads/{threadId}` и `.../messages/{messageId}`

Обращение в поддержку — единственный тред, который остаётся личным
(`threadId` = `support`). Экран «Сообщения» показывает его вперемешку с
чатами по заявкам.

```
// тред
name: string            // «Поддержка»
icon: string            // эмодзи собеседника
kind: 'support'         // по нему модератор собирает обращения одним запросом
unread: boolean         // непрочитанное у клиента; ставит ответ поддержки
lastText: string        // превью и признак «ждёт ответа» для списка
lastFrom: 'user' | 'master'
updatedAt: timestamp

// сообщение
from: 'user' | 'master'
text: string
auto?: true             // автоприветствие: сервер не шлёт о нём пуш
time: string
createdAt: timestamp
```

**Поддержка настоящая.** Раньше ответ подставляло само приложение заготовкой;
теперь тред читает модератор и отвечает из раздела модерации от лица
«Поддержки». Это единственная часть поддерева пользователя, открытая кому-то
кроме владельца, и правила выдают её узко: только тред `support`, только
модератору, писать — только сообщения `from == 'master'`, чужие сообщения не
правятся и не удаляются. Список обращений собирается запросом по группе
коллекций `threads` с обязательным фильтром `kind == 'support'` — без него
запрос зацепил бы личные треды и отклоняется правилами целиком. Превью
(`lastText`, `lastFrom`) денормализовано в тред, чтобы список из полусотни
обращений не читал сообщения каждого.

Важно: правила не наследуются вглубь автоматически, поэтому поддерево
`users/{uid}/{document=**}` описано в `firestore.rules` явно.

## Удаление аккаунта

Требование магазинов приложений: удалить аккаунт можно из самого приложения,
а не письмом в поддержку. Живёт в профиле, подтверждается паролем — Firebase
всё равно требует свежего входа для `deleteUser`, и это же проверка, что
телефон в руках у владельца.

**Удаляет сервер, просит клиент.** Единственная запись, которую делает
приложение, — сама просьба в `deletions/{uid}`. Дальше работает функция
`onDeletionRequested`: она обходит данные этапами (`orders → threads →
verification → master → profile → auth`), отмечая в том же документе, где
остановилась. Обрыв на любом шаге не страшен — повтор продолжит с того же
места, а каждый этап написан идемпотентно.

Раньше весь обход шёл с телефона семью подряд идущими операциями без
транзакции. Сбой посередине оставлял наполовину удалённый аккаунт, а подписка
на профиль тут же создавала удалённый документ заново.

**Клиент всё равно делает свою часть** — тем же порядком, но каждый шаг
терпит неудачу молча. Причина в том, что функции требуют тарифа Blaze, а
удаление аккаунта обязано работать всегда: этого требуют магазины приложений.
Обе стороны идемпотентны, поэтому двойная работа безвредна: что успел клиент,
функция пропустит.

**Заявки не удаляются, а обезличиваются.** Они общие с мастером и служат
историей расчётов, но имя, адрес, комментарий и фотография из них уходят —
это делает функция через Admin SDK, клиенту такие правки правила не дают и не
должны давать. Незакрытые заявки при этом отменяются: мастер не должен ехать
к исчезнувшему клиенту.

Отзывы о мастере остаются: они написаны другими людьми и к его персональным
данным не относятся.

## Если мастер исчезает

Исчезнуть он может двумя способами, и они не равнозначны.

| Что случилось                         | Заявки в работе                                     | Неотвеченные предложения |
| ------------------------------------- | --------------------------------------------------- | ------------------------ |
| Удалил аккаунт (`onMasterDeleted`)    | возвращаются в «Поиск мастера», клиент получает пуш | снимаются                |
| Потерял допуск (`onMasterUnverified`) | остаются                                            | снимаются                |

Разница в том, есть ли ещё человек. Удалил аккаунт — работать некому, и
клиента нельзя оставлять с мастером-призраком. Потерял допуск (например,
отозвал согласие на фотографию) — исполнитель на месте, бросать клиента
посреди ремонта хуже; но браться за новое он уже не вправе.

Заявки в статусе «Ждёт подтверждения» не трогаются ни в одном из случаев:
работа сделана, и отбирать у клиента возможность её подтвердить нельзя.

## Документы и согласия

Тексты живут в `components/legal.ts` — в коде, а не в базе: согласие нельзя
давать вслепую, а связь может пропасть. Версия документа — дата его редакции.

**Заготовки, а не документы.** Тексты написаны как рабочая основа, места для
реквизитов оператора помечены `[В КВАДРАТНЫХ СКОБКАХ]`. До запуска их обязан
посмотреть юрист: приложение собирает имя, email, номер телефона, домашние
адреса и фотографию лица.

**Три документа, два уровня согласия.**

| Документ                    | Когда спрашивается  | Где хранится согласие                                     |
| --------------------------- | ------------------- | --------------------------------------------------------- |
| Пользовательское соглашение | при регистрации     | `users/{uid}.consents.terms`                              |
| Политика конфиденциальности | при регистрации     | `users/{uid}.consents.privacy`                            |
| Согласие на фотографию лица | перед съёмкой селфи | `masters/{uid}/verification/application.biometricConsent` |

Первые два обязательны для всех и проверяются `consentsCurrent()`. Галочка на
экране регистрации снята по умолчанию — предустановленное согласие согласием
не является, — и без неё регистрация не проходит. Согласие даётся до создания
аккаунта, а профиль в базе появляется уже после входа: между этими моментами
его негде держать, кроме модульной переменной в `legal.ts`.

**Что при смене редакции.** Меняется `version` — `ConsentGate` перекрывает
приложение и требует принять заново. Тихо считать старое согласие
действующим для новой редакции было бы обманом. У гейта есть выход «не
принимаю» — отказ не должен вести в тупик.

**Биометрия отдельно.** Фотография лица — не то же самое, что фото поломки, и
общего согласия для неё мало. Правила держат связку: `photoUrl` нельзя
записать без `biometricConsent`, и нельзя убрать согласие, оставив снимок.
Отзыв (в анкете мастера) удаляет файл из Storage и снимает флаг `verified` —
для этого владельцу разрешено понижать себе `verified` с `true` на `false`
(повышать по-прежнему может только модератор).

## Сводка для модератора

В разделе модерации — счётчики по мастерам: проверено, ждут решения,
отклонено, всего анкет. Плюс покрытие: в скольких населённых пунктах есть
мастера, отмечены ли шесть городов республиканского значения и по каким
специальностям мастеров нет вообще. Последнее — самое полезное: это заявки,
на которые некому откликнуться.

**Заявок клиентов в сводке нет, и это не упущение.** Модератор их не читает —
правила отдают заявку только клиенту, назначенному мастеру и проверенным
мастерам по открытым. Считать заявки, дав модератору доступ к ним, значило бы
открыть ему все адреса и фотографии квартир: ровно то, ради ограничения чего
и строилась вся проверка мастеров. Счётчики по заявкам появятся, когда будут
развёрнуты функции: они будут вести числа в отдельном документе, и модератор
увидит статистику, не получив доступа к данным.

**Живого счётчика нет** тоже по устройству: агрегатные запросы Firestore
одноразовые, подписаться на них нельзя. Сводка обновляется при открытии
раздела и жестом «потянуть вниз». Числа берутся агрегатами (сервер отдаёт
количество, не выкачивая документы); анкеты читаются целиком только для
покрытия — по массивам городов и специальностей агрегат не посчитать. При
сотнях мастеров это терпимо, при тысячах покрытие надо будет считать на
сервере.

Настоящего «онлайн» в Firestore нет вовсе: он не замечает, что человек закрыл
приложение. Для этого нужна Realtime Database с `onDisconnect()` — отдельная
база рядом. Дешёвая замена — отметка последнего входа и счётчик «активны за
сутки»; она честнее, чем «онлайн», обновляемый опросом.

## Серверная часть: `functions/`

Cloud Functions на TypeScript. Здесь живёт всё, чему нельзя доверять клиенту.

| Триггер                   | Что делает                                                                                               |
| ------------------------- | -------------------------------------------------------------------------------------------------------- |
| `onOrderCreated`          | новая заявка → пуш **проверенным** мастерам подходящего города и профиля                                 |
| `onOfferCreated`          | предложение → пуш клиенту                                                                                |
| `onMessageCreated`        | сообщение → пуш второй стороне                                                                           |
| `onOrderStatusChanged`    | выбрали / работа сдана / подтверждена / отменена; на «Завершена» пересчитывает `completedOrders` мастера |
| `onVerificationChanged`   | заявка подана → пуш модераторам; вердикт → пуш мастеру                                                   |
| `onSupportMessageCreated` | обращение в поддержку → пуш модераторам; ответ поддержки → пуш клиенту                                   |
| `onDeletionRequested`     | удаление аккаунта этапами, с возобновлением после сбоя                                                   |
| `onMasterDeleted`         | мастер удалил аккаунт → заявки в работе возвращаются в поиск                                             |
| `onMasterUnverified`      | допуск снят → снимаются неотвеченные предложения                                                         |
| `reconcile`               | раз в 15 минут добирает то, что не доехало событиями                                                     |
| `onReviewWritten`         | пересчёт `rating` и `reviewsCount` в анкете мастера                                                      |
| `createCardBinding`       | вызывается приложением, создаёт привязку карты у провайдера                                              |
| `yookassaWebhook`         | подтверждение от провайдера: токен карты и возврат рубля                                                 |
| `requestPhoneCode`        | шлёт одноразовый код входа по СМС, хранит только его хэш                                                 |
| `verifyPhoneCode`         | сверяет код, находит или заводит аккаунт по номеру, отдаёт custom-токен                                  |

**Вход по телефону — свой, а не Firebase Phone Auth.** Встроенный вход по
телефону в веб-SDK требует reCAPTCHA, которой нужен DOM, — в Expo-приложении
без WebView его нет; к тому же СМС от Google в российские сети доставляются
ненадёжно. Поэтому код шлёт наша функция через российского провайдера
(SMS.RU, ключ `SMSRU_API_ID` в `functions/.env`), а вход выполняется
custom-токеном. Коллекция `phoneCodes` закрыта правилами наглухо: документ
называется хэшем номера и хранит хэш кода — утечка не даёт ни войти, ни
узнать номер. Лимиты: минута между отправками, пять отправок в час, пять
попыток ввода, код живёт пять минут и сжигается при входе. В бою сервисному
аккаунту функций нужна роль `iam.serviceAccountTokenCreator` на самого себя —
без неё custom-токен не подписать. У телефонного аккаунта нет пароля: смена
пароля ему не показывается, а удаление аккаунта он подтверждает кодом из СМС
на собственный номер (свежий вход по коду заодно удовлетворяет требование
Firebase о недавнем входе для `deleteUser`).

**Почему на сервере.** Рассылка требует чужих push-токенов, а `users/{uid}`
читает только владелец — с клиента это неисполнимо в принципе. Рейтинг на
клиенте означал бы, что мастер сам выставляет себе оценку.

Пуши уходят через Expo Push API (`exp.host`), потому что токены у нас
экспошные: прямой путь в FCM/APNs потребовал бы сертификатов обеих платформ.
Токены, на которые Expo ответил `DeviceNotRegistered`, вычищаются из профиля —
иначе список растёт вечно и каждая отправка дорожает.

**Требуется тариф Blaze.** На бесплатном Spark функции не разворачиваются.
Пока их нет: рейтинг не считается (в интерфейсе честно пусто вместо звёзд),
а уведомлений не приходит совсем. Локальные уведомления, которые раньше
показывались при открытом приложении, убраны намеренно — иначе после деплоя
каждое событие приходило бы дважды. Последним из них был поддельный ответ
поддержки: теперь на обращения отвечает модератор из раздела модерации,
и пуши о них шлёт сервер, как обо всём остальном.

Выборка «кому слать» в `onOrderCreated` делается в памяти: у Firestore нет
запроса «город совпал ИЛИ город не указан». На тысяче мастеров стоит
переписать на запрос с индексом — в коде стоит лимит и предупреждение в лог.

Деплой:

```
firebase deploy --only functions
```

## Структура приложения

Приложение одно, живёт в корне репозитория: Expo SDK 54 + expo-router.

```
app/
  _layout.tsx          провайдеры, Stack, оверлей режима мастера
  (tabs)/
    _layout.tsx        Tabs со своей плавающей панелью вместо штатной
    index.tsx          «Заказы» — изометрический дом
    messages.tsx       «Сообщения»
    profile.tsx        «Профиль»
components/
  AppState.tsx         общее состояние и все действия над ним
  ConsentGate.tsx      блокирующий экран при смене редакции документов
  firestoreError.ts    код ошибки → текст: отказ по правам ≠ «нет связи»
  format.ts            rub / склонения / рейтинг — общее для обеих сторон
  legal.ts             тексты документов, версии, проверка согласий
  serviceOptions.ts    дерево услуг, специальности, нормализация города
  verification.ts      статусы проверки мастера и запуск привязки карты
screens/               сами экраны, не знают про роутер
  AdminScreen.tsx      модерация, оверлей поверх всего — как режим мастера
  LegalScreen.tsx      чтение документа, открывается поверх любого экрана
functions/             Cloud Functions, отдельный проект со своим package.json
tests/                 тесты правил доступа
```

Маршруты в `app/` — тонкие адаптеры: берут данные из `AppState` и передают
экрану ровно те же пропсы, что раньше передавал `App.tsx`. Поэтому экраны
ничего не знают ни о навигации, ни о хранилище — Firestore целиком спрятан в
`AppState.tsx`. Исключение одно: `MasterScreen` ходит в базу сам, потому что
данные режима мастера не нужны остальному приложению.

Панель вкладок — своя (`components/BottomTabs.tsx`), плавающая, умеет
прятаться под шторками. Штатная панель навигатора отключена
(`tabBar={() => null}`), а своя отрисована соседом поверх него, чтобы
сохранить absolute-позиционирование.

Изначально планировалось наоборот — перенести экраны корня в скаффолд
`podrukoy2/`. Направление развернули: в корне было 4026 строк отлаженного
интерфейса против 1553 строк преимущественно шаблонного кода, поэтому
дешевле и безопаснее оказалось внести роутер в корень. `podrukoy2/` удалён,
из него забрали `firebaseConfig.ts`.
