# Изменение данных Firestore

Пять шагов. Пропуск любого ломает не сборку, а прод.

## 1. Схема

`ARCHITECTURE.md`, раздел «Модель данных». Правила написаны ровно под неё —
меняете одно, проверяйте второе. Там же записано, **почему** поле такое: без
этого следующая правка вернёт то, что уже отвергли.

## 2. Правила

`firestore.rules`. Держите в голове, что правила не фильтруют выдачу: Firestore
проверяет их против **запроса**, а не против результата. Если запрос способен
вернуть документ, который правило запрещает читать, падает весь запрос целиком.
Поэтому фильтр по владельцу должен стоять в самом запросе, а не подразумеваться.

## 3. Тесты

`tests/firestore.rules.test.mjs`, 103 теста. Разбиты по сценариям
(«Выбор мастера клиентом», «Что клиент менять не вправе»), а не по коллекциям —
добавляйте в подходящий `describe`, а не в конец файла.

Новое правило — минимум два теста: кому можно и кому нельзя. Второй важнее:
именно `assertFails` ловит регрессии, `assertSucceeds` только подтверждает, что
вы не сломали очевидное.

## 4. Индексы

Запрос с двумя и более условиями, либо `where` плюс `orderBy` по другому полю,
требует записи в `firestore.indexes.json`. Без неё он падает **в рантайме** —
то есть у пользователя, а не при сборке.

Две ловушки, обе уже встречались здесь:

- **Необязательные фильтры.** Лента мастера в `screens/MasterScreen.tsx:314`
  собирается динамически: город и категория добавляются, только если заполнены.
  Каждая достижимая комбинация — отдельный индекс. В `firestore.indexes.json`
  их поэтому четыре штуки на `orders`, а не один.
- **`collectionGroup`.** Запрос по группе (`offers`, `verification`) требует не
  только составного индекса с `"queryScope": "COLLECTION_GROUP"`, но и записи в
  `fieldOverrides` — иначе поле индексируется только в пределах коллекции.

## 5. Выкатка

Правила и код уезжают вместе. Код без правил открывает данные, правила без кода
ломают работающий экран.

```bash
npm run rules:deploy      # firestore: правила + индексы, пишет отпечаток
npm run storage:deploy    # storage: отдельно, нужен Blaze
```

Раздельно, потому что раздельно и ломаются: Storage может быть не подключён, и
его падение не должно отменять выкатку правил Firestore. Отпечаток в
`.rules-deployed.json` пишется только для того, что действительно уехало, —
`npm run rules:check` потом покажет расхождение.

## Персональные данные

В коллекцию `audit` кладут только идентификаторы и перечисления: журнал
переживает удаление аккаунта, и имя или адрес в нём обошли бы собственное же
удаление данных. Проверка в `functions/src/audit.ts` вырезает похожее на почту
и телефон, но это последний рубеж, а не разрешение складывать туда что попало.
