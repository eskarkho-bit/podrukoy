# Обязательные проверки

Изменение не готово, пока все семь не зелёные. Не «почти готово» — не готово.

Порядок от быстрого к медленному: незачем ждать эмулятор ради опечатки в типах.

```bash
npx tsc --noEmit                    # 1. типы приложения
npm --prefix functions run build    # 2. типы и сборка функций
npm run lint                        # 3. eslint
npm run format:check                # 4. prettier
npm test                            # 5. 106 тестов компонентов
npm run test:rules                  # 6. 117 тестов правил доступа
npm --prefix functions test         # 7. 76 тестов функций
```

Формат чинится сам: `npm run format`. Часть находок линтера — тоже,
`npm run lint:fix`, но зависимости эффектов он не трогает, и правильно
делает: там нужна голова.

Второй шаг в `AGENTS.md` записан как `cd functions && npm run build` — это то же
самое. Форма с `--prefix` работает и в PowerShell, где `&&` не существует.

## Эмулятор для шестого и седьмого шага

Идёт на Java, `firebase-tools` требует JDK 21 или новее — `java -version`, если
шаг падает на запуске. Первый прогон скачивает бинарник эмулятора, дальше он
берётся из кэша. Порт может остаться занятым после прерванного прогона: тогда
падение будет про порт, а не про правила.

Шаги 6 и 7 поднимают эмулятор каждый свой и оба занимают порт 8080 — запускать
их одновременно нельзя.

`firebase-tools` объявлен в корневом `package.json`, в `functions/` его нет.
Локально это незаметно: npm подставляет `node_modules/.bin` родителя в PATH.
Но `npm --prefix functions test` без корневой установки падает на «firebase не
найден» — это уже роняло CI.

## Как читать падения

**Тесты правил.** Сначала решите, что неверно: тест или правило. Тесты
описывают инварианты — кто и чего **не** может, — а не текущее поведение кода.
Ослабить правило, чтобы тест прошёл, значит открыть чужие адреса и заявки.
Так нельзя. Правила — единственное, что стоит между пользователями и чужими
данными.

**Тесты функций.** То же самое, но про деньги: они описывают, что повтор
вебхука не делает второй возврат, а обрыв удаления аккаунта возобновляется.
Провайдер подменён, Firestore настоящий — если тест упал на записи в базу,
дело в коде, а не в заглушке.

**Типы функций.** `functions/` собирается своим `tsconfig.json` и своей копией
зависимостей. Ошибка там не видна первому шагу и наоборот.

**`react-hooks/exhaustive-deps`.** Не добавляйте зависимость не глядя.
Значения `useSharedValue` стабильны — их дописать безопасно. А функция,
пересоздаваемая каждую отрисовку, в зависимостях означает эффект на каждый
рендер; если внутри запись в Firestore, это счёт от Google. Такие держат
в `useRef` или закрепляют `useCallback`.

**`no-floating-promises`.** Работает только с типами. Если правило вдруг
перестало находить подброшенный висячий промис — значит, в `functions/`
не установлены зависимости, а не значит, что код чистый.

## Две проверки рядом, обе не блокирующие

`npm run rules:check` — не про код, а сторож деплоя: не отстали ли правила в
бою от репозитория. Красный до первой `npm run rules:deploy` — это ожидаемое
состояние, чинить код по нему не надо.

`npx expo-doctor` — сверка версий пакетов с SDK 54. Ходит в сеть и потому
иногда падает не по делу; в CI стоит `continue-on-error`. Запускать стоит после
установки любого пакета — и ставить только через `npx expo install`, иначе
версия разъедется с SDK.

## Чего не проверяет никто

Экраны целиком не покрыты — тесты компонентов берут чистые функции
(`format`, `cities`, `legal`, `verification`) и один `ActionSheet`; сами
экраны проверяются руками или через preview. Живой связки «приложение ↔
функции» тоже нет: каждая сторона проверена отдельно.
